## Why move off the bit-banged GPIO oscillator

This session traced the moisture reading's long-standing "locks onto a value for hours, then jumps" behavior (see `scindapsus_probe_charge_settle_bug` history) past the 2026-07-28 charge-settle poll-loop fix, which did not fully resolve it. Root cause: `countOscCycles()`'s outer sampling window is gated on `millis()`, which on this chip derives from RTC1 running off the raw 32.768kHz LFCLK (~30.5us hardware tick — the same clock `lowPowerDelay()`'s own comment already documents at ~1024Hz). At the shipped 1ms window, that tick granularity is ~3% of the whole window, and since all 5 median samples in one reading inherit the same tick-phase offset (each burst starts right where the previous one's tick-aligned exit left off), the artifact shows up as a stable plateau that jumps cleanly to a different stable plateau rather than continuous jitter.

Confirmed via the full Supabase history (`msv2_sensor_history`, sensor 1, receiver `MSV2088A3104A7AC`, 10,917 readings over 6 days): the raw-value distribution is a genuine comb, not a curve — populated levels with real gaps between them, peak-to-peak spacing close to constant (~7-16 units, avg ~11-12) across the *entire* dry-to-wet range. That constancy (not scaling with the reading) is the fingerprint of a fixed time-quantum artifact, not a soil-physical effect. Cross-checked against wake-counter resets and BLE RSSI: only 9% of jumps line up with a reboot or physical handling; 91% happen between consecutive un-reset wake cycles with normal RSSI, and 106/172 are immediate hop-then-return pairs — consistent with a measurement-side bistability, not the probe being moved. Widening `OSC_SAMPLE_WINDOW_MS` (1ms -> 5ms, already applied in this file) mitigates it but doesn't remove the underlying class of problem: any software-timed gate window inherits RTC tick granularity, at whatever ratio the window size buys you.

Decision: rather than keep tuning window size and MCU-side timing workarounds, move the actual oscillation and threshold-detection off the MCU entirely, onto a part built for it.

## Chosen approach: FDC2212 (TI), not a discrete 555 front end

Both a dedicated capacitance-to-digital IC and a from-scratch 555-based analog front end (astable + monostable pair as an F-to-V converter, or a 555 astable read digitally into a hardware timer-capture) were evaluated. FDC2212 was chosen. Full reasoning is in this session's chat log; summary:

- **Reference cancellation, not just lower noise.** FDC221x measures the sensor LC tank ratiometrically against an internal reference, which is architecturally why it resists VDD/temperature drift. A discrete 555 pair has no such cancellation — thermal drift, battery-voltage drift (a real second axis distinct from temperature, since this runs off a discharging LiPo), and unit-to-unit comparator/passive-tolerance variation all stack directly into the reading, requiring per-probe characterization every time one is built.
- **Power, once fairly compared, is close — but only one side gets there for free.** TLC555 active current (250uA) is actually *lower* than FDC2212 active current (2.1mA). But the TLC555 has no native sleep/shutdown state; left powered it draws 250uA continuously for the full 10s wake period, ~100x worse than a properly-duty-cycled FDC2212 (~2.5uA average at this session's estimated active-window length, using shutdown between reads: 200nA shutdown / 35uA sleep / 2ms and 0.05ms real datasheet wake latencies respectively). Matching that on the 555 side requires adding external power-switching hardware (MOSFET/load switch + GPIO control + your own bench-characterized startup/settling time, since that's not a datasheet-guaranteed spec the way it is for the FDC part) — achievable, but it's added hardware and validation risk the FDC2212 doesn't need, since its low-power modes are a register write away.
- **Built-in EMI deglitch filter and error/status reporting** (data-range clamping to known sentinel values, amplitude-out-of-range status bits) — a bare 555 timing network has neither; both would need to be reinvented in firmware.
- **Cost is the honest tradeoff the other way**: ~$7 (FDC2212DNTR) vs. a ~$2-3 discrete BOM. Given the design/debugging time already sunk into the MCU-timing side of this problem this session, that gap is small.

## Design parameters

- **Sensor capacitance target**: TI's own guidance for this LC-tank architecture recommends **300pF-2nF**. This is the window the *total* tank capacitance (padding + sensor) needs to sit in — not a requirement on the sensor's bare capacitance alone.
- **Measured/derived current probe capacitance**: using the current 56kOhm pulldown (confirmed: Scindapsus = 56kOhm, Alocasia = 100kOhm — the firmware's old "10k" comment is stale) and an observed 200-300kHz oscillation range at a 3.3V->1.3V discharge swing, derived capacitance is **~64-96pF** — below TI's window. This is a rough estimate (single-exponential RC model, eyeballed frequency band, doesn't account for possible inter-plate mutual-capacitance coupling in the dual-plate drive), not a lab measurement — **see Open Items**.
- **Padding capacitor — superseded 2026-09-14**: the original design added 270pF C17 to target ~300-370pF total. C17 is now DNP after the capless Probe 8 test; production uses only the connected tank and prohibits the out-of-range disconnected tank.
- **Inductor**: 5-10uH, shielded preferred, self-resonant frequency >= ~2x the actual sensing frequency for margin. At L=5-10uH against a ~300-370pF total tank, sensing frequency lands around 1.3-4.1MHz, so target inductor SRF >= ~8MHz, ideally well above. Candidate part found and priced: Coilcraft **0805LS-682XGRC** (6.8uH, SRF 35MHz, 0805 package, ~$2.13/unit at DigiKey single-piece pricing) — unshielded; a shielded equivalent in the slightly larger 1008 package is the fallback if shielding turns out to matter in practice.
- **Padding margin**: size against the *full* historically-observed range, not just the narrow "typical" 200-300kHz band — the 6-day history showed real, if less frequent, excursions wider than that (handling events, disconnection-adjacent readings). Padding tight around only the common case risks exactly the events most worth catching cleanly (right after watering, or when the probe's handled) pushing the reading into the chip's under/over-range clamp.

## Electrode polarization mitigation (still needed with the FDC2212)

Switching to an LC-tank front end does not automatically remove the polarization problem the dual-plate bipolar-drive fix (commit `45578e5`) was built to solve. The tank's oscillation is AC at the sensing frequency, but the FDC2212 sense pin sits at a positive DC operating point with that AC riding on top (single-supply chip; this is what the 1.2-1.8Vpk oscillation-amplitude spec describes) — it is not a symmetric bipolar swing around 0V. If the tank is wired the straightforward way (electrode A into the sense node, electrode B hard-tied to ground/reference), electrode A sits at a persistent positive DC average relative to electrode B indefinitely, which is exactly the one-directional electrochemical migration/fouling condition the old single-plate design suffered from.

**Plan:** periodically swap which physical electrode is the sense node and which is the reference node, on a slow (minutes-scale) timer — electrochemical migration builds up over minutes-to-hours, so this is plenty fast to prevent net long-term bias while far too slow to interfere with the MHz-range sensing itself. Drive this from the existing MCU wake loop (a counter checked every N wake cycles) rather than a dedicated timer IC — the nRF52840 is already awake on a schedule and has spare GPIOs, so this costs a few lines of firmware and zero extra components.

**Switching hardware — decided: 74HC4052, not 74HC4053.** Originally scoped as a 74HC4053 (three independent SPDT/2:1 channels) purely for the polarity swap above, which only needs a DPDT (2-pole, double-throw) crossbar — 2 SPDT functions, not a full H-bridge (an H-bridge is for bidirectional load *driving*, a different problem than routing which of two fixed chip-side nodes connects to which electrode). But folding in the conductivity-check circuit below changes the requirement: each electrode now needs to reach **four** distinct destinations, not two (see the mode/phase table below), which is a 4:1 selection per electrode. **74HC4052** (dual 4-channel analog mux, two independent SP4T switches sharing one 2-bit select pair, ~same price class as the 4053, well under $1/unit) is the right-shaped part: one channel's common pin per electrode, four throw pins per channel wired to `{TANK_HOT, VDD, TANK_REF, DIV_NODE}` in a rotated order between the two channels so the shared 2-bit code always produces valid, non-conflicting routing. Two GPIO pins total.

**Caution:** the switch's own on-resistance and parasitic (off-state) capacitance now sit inside the sensitive LC tank path. Verify on the bench (same ring-down test already planned for capacitance/inductor validation) that it isn't dragging down Q or shifting the resonant frequency meaningfully once inserted - pick a switch spec'd for low RDS(on) and low COFF, don't assume it's transparent.

## Salt/conductivity compensation

The cave pearl project's writeup on hacking a 555-based capacitive soil sensor (thecavepearlproject.org, 2020-10-27) independently confirms a mechanism relevant here: dissolved salts/ions affect capacitive soil readings **until roughly 20-30MHz**, well above the ~1.3-4.1MHz this design's tank runs at. Moving to the FDC2212 fixes the *polarization* problem (resolves fine at MHz-range frequencies) but does **not** fix salt/conductivity confounds - this directly connects to the earlier "moisture equilibrium keeps rising after each watering" investigation, where mineral/fertilizer buildup was the leading hypothesis. Higher frequency helps this on a gradient (the ionic double-layer's contribution shrinks progressively with frequency, not a hard cutoff), so pushing somewhat above the current ~1-4MHz target - if inductor SRF margin allows - buys some improvement, but true escape needs true RF, which is out of scope here.

**Considered and ruled out: reading `CH0_IDRIVE` back as a live conductivity proxy.** The register is R/W over I2C, so it's technically readable, but it does not auto-adjust - it's a static, open-loop value set once via bench characterization (per the datasheet's own recommended procedure: scope the oscillation amplitude, hand-tune IDRIVE until it lands in the 1.2-1.8Vpk window, bake that fixed value into firmware). Reading it back only tells you what was last written, not anything live about current soil loading. The dynamic signal that does exist - `ERR_AHW`/`ERR_ALW` amplitude warning status bits, which assert if a fixed IDRIVE can no longer sustain the target amplitude against a lossier load - is binary (in/out of window) rather than continuous, and carries the same "not always reliable in practice on this part" caveat already noted from the TI E2E forum.

**Chosen approach: a brief, switched resistive (EC) measurement using the same mux, sharing the electrodes.** Periodically (tied to the same swap-phase state as the polarization mitigation, not a separate timer): drive one electrode to VDD and route the other through a known resistor to true ground, then read the ADC voltage at the resistor's electrode-side terminal (`DIV_NODE`) before switching straight back to oscillating mode. `DIV_NODE` *is* the divider midpoint (`R_soil` in series with the known resistor) - no separate ADC-routing channel needed, just a fixed ADC pin on that node.

Four things that have to be right for this to actually work, not just conceptually:
- **`DIV_NODE` is not the same node as `TANK_REF`, even though both eventually reference ground.** `TANK_REF` needs zero series impedance for clean tank operation; `DIV_NODE` needs a deliberate, non-zero series resistance for the divider to produce anything other than a flat 0V. Merging them breaks one function or the other. Naming it `DIV_NODE` rather than the earlier working name (`R_GND`) specifically to avoid implying it's interchangeable with true ground.
- **The measurement must be brief and pulsed, not a sustained DC hold** - holding a static bias across the electrodes reintroduces the same electrochemical polarization problem this whole scheme exists to avoid, now corrupting the EC reading itself (matches the cave pearl article's own advice for EC measurement: read fast, then de-power and rest).
- **Settling-time tension to characterize on the bench:** too fast and the ADC reads the parallel soil-capacitance's charging transient rather than the settled resistive divider value; too slow and polarization starts corrupting the reading. Given the sensor's capacitance is only tens-to-low-hundreds of pF, the capacitive settling time should be quick (µs range) relative to when polarization becomes significant, but this is a real window to verify, not assume.
- **The existing physical pulldowns (56kOhm, one per electrode, already on the Scindapsus board) cannot stay permanently wired as-is.** They're useful for the EC divider (the measured-side one can double as the known resistor, free reuse) but actively harmful for oscillating mode - a ~56kOhm resistor permanently in parallel with an MHz-range LC tank will likely damp Q meaningfully. Whatever resistor ends up serving the EC measurement needs to be part of the switched network (connected only during the EC-check phase), not hardwired the way the current board has it.

Mux routing table (2 GPIO select bits, `mode` + `phase`):

| mode | phase | Electrode A -> | Electrode B -> |
|---|---|---|---|
| 0 (oscillating) | 0 | TANK_HOT | TANK_REF |
| 0 (oscillating) | 1 | TANK_REF | TANK_HOT |
| 1 (EC check) | 0 | VDD | DIV_NODE (known R to GND) |
| 1 (EC check) | 1 | DIV_NODE (known R to GND) | VDD |

## 2026-08-01 PCB layout review (MSV3_Probe_PCB, Altium)

First layout pass reviewed on the real board (schematic + PCB screenshots this session). Two things worth flagging up front:

**Part discrepancy: the schematic uses FDC2214RGHR, not FDC2212.** Everything above (design parameters, sensor capacitance target, inductor selection) was written against FDC2212 (2-channel). The actual placed part is FDC2214 (4-channel, same family, pin-compatible mux/register model as far as this doc's math goes, but confirm the channel count difference doesn't change anything before finalizing - e.g. if only one channel is used, the other three's pins still need proper termination/handling per the datasheet rather than being left floating). Reconcile this doc's title/part references with the real BOM before implementation.

**Component-library gotcha hit and resolved:** the FDC2214RGHR SchLib symbol had a Footprint model entry (`QFN50P400X400X80-17N`) that was just a typed name, not actually linked to a PCB library file - Altium's ECO reported `Footprint Not Found` and cascading `Unknown Pin` errors on all 17 pins as a result. Fixed via the SchLib's Footprint model dialog: PCB Library -> Library path -> Browse to the actual `.PcbLib` file, then Browse again (footprint-name picker) to select the footprint from the list rather than trusting a typed string. Worth remembering for every future custom part in this project - a Models entry with a name and no resolved library link will silently fail exactly this way.

**Electrode routing (Node A/B) findings, from the real layout:**

- **Ground/power pour is not cleared under the sensing path.** Both the top and bottom copper pours run essentially solid straight through the Node A/B traces and pads - no keepout at all. This directly adds board-parasitic capacitance into the same tank the FDC2214 is trying to measure, on top of whatever the electrode-swap mux (see below) already contributes. This is the single highest-priority layout fix before this board is trusted for real calibration.
- **Node A/B are length-mismatched:** measured 44.467mm (Node A total) vs. 52.424mm (Node B total) - about 8mm / ~18% relative difference. For a differential sensing pair that's a real asymmetry, not noise.
- **Fix, once the mux part (below) is finalized and the board is re-routed:**
  - Clear plane pour along the *entire* sensitive path - FDC2214 pin -> trace -> mux common pin(s) -> mux channel pin(s) -> trace -> Node A/B/connector - not just the last stretch nearest the connector. Anything upstream on the main board is still "outside the sensor box" and still dilutes the measurement if a plane sits under it.
  - Clear *selectively*: only under the mux's analog signal pins (common + the four channel pins), not under its VCC/GND/digital-select pins - those still want solid plane reference and aren't part of the LC loop.
  - Keep the keepout no larger than needed, and don't route unrelated high-speed/digital nets (SWD, USB, BLE feed) across the cleared region - they'd lose their own return-path plane exactly where they cross it.
  - Vias are unavoidable given the mux sits physically between the sensor and the IC - that's fine. Minimize count (1 per net if at all possible), keep the count and placement matched between Node A and Node B so any parasitic they add is symmetric rather than something that unbalances the differential reading, and use the smallest anti-pad the fab process allows.
  - If noise on unselected channels persists after all of the above, a grounded guard trace alongside the sensitive traces is the next escalation - not a first-line fix, since it adds its own parasitic capacitance.

**Electrode-swap mux part: 74HC4052D is what's actually in the schematic, and it's very likely inadequate.** This doc's "Electrode polarization mitigation" section above already flagged (line "Caution: the switch's own on-resistance and parasitic...") that the swap mux's RON/COFF needed bench verification before trusting it. This session's finding resolves that open item in the negative *before* reaching the bench: the 74HC4052 is a general-purpose logic-level CMOS switch (same family this project already moved away from for MCU timing reasons), not an RF/precision analog switch, and its known characteristics make it a poor fit here regardless of bench results:

- **RON** typically ~70-120 ohm at these supply levels, and gets worse (higher) as VCC drops toward the 3.3V/LiPo range this probe actually runs at - sitting in series inside the LC tank's loop, this is enough to meaningfully drag down Q and oscillation amplitude.
- **Analog bandwidth** is only well-characterized into the low single-digit MHz range for this part family - not clean across this design's ~1.3-4.1MHz target tank frequency, and further from clean the higher the sensing frequency ends up after final component selection.
- **COFF** (several pF typical, unselected-channel coupling onto the common bus) adds cross-talk risk between the electrode-swap states.

**Recommended replacement: TI TMUX1574** (or a sibling in the TMUX15xx/16xx precision-mux family) - a dual 4:1 precision analog switch explicitly positioned as a modern, RF-capable replacement for the CD4052/74HC4052 architecture: single-digit-ohm RON, much lower COFF, bandwidth well past this design's sensing range. It is a true bidirectional CMOS switch like the 4052, so the electrode-swap/EC-check routing table in "Electrode polarization mitigation" above doesn't need to change conceptually - only the part number and its footprint/pinout. **Verify current RON/bandwidth specs and pinout against the live TI datasheet before finalizing the BOM/footprint** - the numbers above are from general knowledge of the part family, not a fresh datasheet pull this session.

**CORRECTION 2026-08-10: TMUX1574 doesn't work - wrong switch topology, not just an unverified spec.** Pulled the real TI datasheet/product page this session. TMUX1574 is **4 independent 2:1 (SPDT) switches sharing one common `SEL` pin** (pinout: `SEL, EN, S1A/S1B/D1, S2A/S2B/D2, S3A/S3B/D3, S4A/S4B/D4`) - a single select bit flips all four switches together between position A/B. That cannot implement the `mode`+`phase` routing table above, which needs each node's common pin independently steered to 1-of-4 channels via 2 select bits. It is *not* the "dual 4:1 mux" this doc assumed - that assumption (from general part-family knowledge, never datasheet-verified until now) was wrong.

**Corrected replacement: TI TMUX1309** - datasheet-confirmed "4:1, 2-channel mux": two independent 4:1 muxes (Node A, Node B) sharing 2 select pins, which is exactly the routing table's topology. Verified specs (TI product page, 2026-08-10): RON 59Ω typical (max not yet confirmed - still open), COFF 11pF typical, bandwidth 500MHz (-3dB), VDD 1.62-5.5V, 16-pin (SOT-23-THN/WQFN/TSSOP options). Tradeoff vs. the TMUX1574 numbers above (which belong to a different part and don't transfer): RON is only a modest improvement over the 74HC4052's ~70-120Ω, not the dramatic single-digit-ohm win originally assumed. COFF/bandwidth still aren't binding constraints at this design's ~1.3-4.1MHz tank frequency. **Still need RON max (not just typical) from the actual datasheet table before finalizing** - a Mouser fetch for that number timed out this session.

**Refined pick 2026-08-10: TI TMUX1109, not TMUX1309, once the actual constraint set is "small package + must switch a sensing trace with no ground plane underneath it"** (the Node A/B plane-clearance fix above means the trace feeding the mux is an unshielded, floating, high-impedance node - so the switch's own leakage current and charge injection onto that node matter as much as RON, not just RON/bandwidth/COFF). TMUX1109 datasheet title: *"5V, ±2.5V, Low-Leakage-Current, 4:1, 2-Channel Precision Multiplexer"* - same dual-4:1/2-select-pin topology as TMUX1309, but purpose-built for exactly this class of high-Z sensing signal:

3 pA leakage and 1 pC charge injection are the numbers that matter here: with no ground plane to shield or reference the trace, DC leakage from the switch directly loads a high-impedance floating electrode, and charge injection at each swap event directly kicks the LC tank. Neither TMUX1309 nor the 74HC4052 publish these specs at all, which itself is a signal they're not designed for this class of load. RON is also ~25-30x better than TMUX1309, a genuine bonus not just a wash.

**Real tradeoff to account for:** CON (on-state capacitance) is 38pF, notably higher than TMUX1309's 7pF. This adds directly to whichever node is currently selected into the LC tank - it's a fixed, common-mode addition (present symmetrically on Node A and Node B whenever a channel is selected), so it should fold into the tank's capacitance budget as a constant offset rather than a source of asymmetry. Under the 2026-09-14 capless policy, account for it in the total connected tank and frequency margin; do not add a padding capacitor.

**Still open before finalizing:** COFF (off-state/unselected-channel capacitance) wasn't found in the sources pulled this session (LCSC/TI product pages don't list it) - pull the full datasheet PDF table before finalizing to confirm unselected-channel crosstalk is still low; RON *max* (not just typical) is also still unconfirmed, same open item as TMUX1309 above. TMUX1309 remains a viable fallback (same architecture, easier RON-max data availability) if TMUX1109 stock/cost/hand-assembly (UQFN is leadless) becomes an issue.

## 2026-08-09 Field confirmation: battery-voltage coupling is real and currently happening, not just theoretical

The "Why move off the bit-banged GPIO oscillator" section above already names battery-voltage drift as a reason to move to the FDC2212 (alongside RTC-tick quantization, which was the primary driver at the time). This session found concrete field evidence of it, independent of the quantization issue, plus a precise mechanism for *why* it happens and *why* the FDC2212 avoids it - worth recording since it changes this from "a plausible theoretical concern" to "an observed, currently-active problem with the deployed probes."

**Evidence.** Reviewing a fresh 5-day Supabase window for Scindapsus: 67.6% of all readings are the single value 222 (pinned at the sensor's ceiling), tightly correlated with the probe's battery sitting at/near 0% for the same stretch. Separately, the user observed large moisture jumps specifically correlating with active battery charging - a distinct symptom from the low-battery pinning, but the same root cause.

**Mechanism.** `countOscCycles()` is pure GPIO: `digitalWrite(SENSE_PIN, HIGH)` charges the sense node to whatever VDD currently is, and the discharge is timed against `digitalRead(SENSE_PIN) == HIGH`, whose trip point is also a fraction of VDD. Both the charge target and the read threshold are **ratiometric to the supply rail** - there is no fixed, independent voltage anywhere in the measurement. In principle a perfectly ideal ratiometric threshold would cancel VDD algebraically out of the RC-charging equation, but real silicon doesn't hold that cleanly: input-buffer propagation delay changes with VDD (transistors switch slower at lower VDD), GPIO output drive impedance shifts with VDD (changing the effective starting point of the discharge curve), and threshold hysteresis isn't perfectly linear across the supply range. Those second-order effects are exactly what leaks battery voltage - whether sagging from discharge or disturbed by charge-current IR drop and charger switching noise - into the frequency reading. Note this isn't specific to bit-banging on the MCU: a literal discrete 555 timer has the same flaw, since its internal comparators are themselves referenced to fixed fractions of VDD (1/3, 2/3) with no external reference either. The problem is inherent to *any* simple RC-relaxation-oscillator design, not just this implementation.

**Why the FDC2212 actually avoids it - and it isn't "because it has a reference," more precisely why.** Per TI: *"The digitized sensor measurement... represents the ratio of the sensor frequency to the reference clock."* Two things stack together: (1) an LC tank's resonant frequency is `f = 1/(2π√(LC))` - a function of the inductor and capacitor values only, not of supply voltage, as long as oscillation amplitude is sufficient to be detected at all; (2) that frequency is counted against a **reference clock** (crystal or precision internal oscillator), a time-domain reference, not a voltage-domain one. The measurement moves entirely out of the voltage domain, rather than just getting a "better" voltage reference. (There's almost certainly a bandgap reference somewhere on-die too, most likely regulating the `IDRIVE` current source that sustains oscillation amplitude - see the datasheet-recommended IDRIVE bench-tuning procedure already noted above - but that's a supporting piece, not the primary mechanism.)

**Implication for timeline.** This doesn't change the migration plan, but it does mean the coupling isn't just an edge case at the extremes of the battery curve (dead or actively solar-charging) - it's visibly corrupting data on a probe that's simply had a rough week, which is a fairly normal operating condition, not a rare fault. Strengthens the case for prioritizing this migration, and also motivates a cheap interim firmware mitigation (discard/flag moisture samples while charging or below a battery floor) worth doing regardless of the hardware timeline - see `docs/STATUS_HANDOFF.md`'s 2026-08-09 section.
